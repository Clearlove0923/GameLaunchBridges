# 游戏桥接器制作 Prompt

填写下面的信息后，将整个文本框复制给具备本地文件、编译与进程诊断能力的 AI 编程助手。未知项填写“待识别”，不必事先知道本体路径或启动参数。此 Prompt 可独立使用，不要求安装 Skill 或访问本仓库。

开发过程中需要你配合官方登录、进入游戏、检查语音和正常退出。AI 无法接触实机时，应先交付 Capture 和采集步骤，待拿到证据后继续，不能宣称游戏启动已验证。

## 可直接复制的 Prompt

```text
请为下面的 Windows 游戏开发一个启动桥接器。请实际检查项目、编写代码、构建和验证，不要只给设计建议。以本游戏的真实启动证据决定方案，不照搬其他游戏的参数或目录结构。

【项目资料，由我填写】
- 游戏中文名：<填写>
- 英文项目名（用于目录和 EXE，例如 ExampleGame）：<填写>
- 渠道/区服：<填写或待识别>
- 游戏及官方启动器版本：<填写或待识别>
- 游戏安装目录：<填写本机路径或待识别>
- 官方快捷方式或启动入口：<填写路径或待识别>
- 已知游戏本体：<填写或待识别>
- 源码工作目录/仓库：<填写>
- 已知问题及已有日志：<填写；没有则写无>
- 目标使用方式：<双击 / Steam / 其他启动器，可多选>
- 启动器窗口偏好：<默认自动隐藏，遇到登录、更新或错误时恢复>
- 其他需求：<填写；没有则写无>
- 实机操作范围：<例如可启动 Capture 和游戏；登录由我手动完成>
- 是否需要提交/推送/发布：<默认仅本地开发，未指定则不推送或发布>

【目标和边界】
制作一个位置稳定的单 EXE 入口，完成路径发现、可靠启动或附着、真实游戏进程跟踪和退出清理。配合 Steam 跟踪实际游戏生命周期，不伪造在线状态。

保留必要的官方登录、资源检查、SDK 和反作弊流程。不修改官方 EXE、配置或反作弊组件，不注入、不伪造父进程、不绕过认证。我的安装路径只用于本机验证，不得写死进源码和示例配置。

先读取项目中适用的 AGENTS.md、README 和已有实现。保留其他未提交改动，只修改本任务相关内容。缺少非关键资料时先只读识别；只有无法继续的关键信息才向我询问。涉及登录或游戏内功能验证时，提供明确步骤让我配合，不能代替我报告验证成功。

【第一阶段：判断本体能否直接启动】
1. 识别官方入口、可能的包装入口和真实游戏本体，记录版本、文件属性及现有进程的完整路径、PID、创建时间。不要仅凭 EXE 名称判断角色。
2. 在允许的实机范围内，以已确认的路径、合理的工作目录和有来源的参数进行最小直启验证。路径/工作目录不明确时先采集，不将调用错误当作“游戏禁止直启”。不猜测并批量尝试参数，也不反复盲目提权。
3. 判断成功必须区分：创建进程、出现窗口、进入可操作游戏画面、登录正常、语音/音效正常、反作弊正常和正常退出。进程出现、退出码 0、编译或自动测试通过都不能单独证明游戏可用。
4. 如果直启满足目标场景，采用最小的发现、启动和生命周期桥接；记录首次运行、冷启动和登录缓存等尚未覆盖的边界，并核对官方启动方式。
5. 如果直启失败、依赖后台启动器，或能进游戏却缺语音/功能，先制作 Capture，再决定启动逻辑。已有当前版本、渠道的完整采集证据时可复用，只补缺失项。

【第二阶段：制作 Capture，捕获官方正常启动】
先制作独立的只读诊断工具，验证采集范围和脱敏后，再让我通过官方入口完成正常启动、进入游戏和退出。Capture 源码、构建和测试与该游戏源码一起保存，不默认作为正式桥接器附件。

按需采集：
- 采集时间与时区、渠道、版本、冷/热启动状态、官方图形设置。
- 官方快捷方式目标、启动参数、工作目录及与本游戏有关的协议入口。
- 官方入口→运行时/SDK 宿主→包装入口/反作弊→本体的实际进程接力。
- 关键进程的 PID、父 PID、创建时间、完整路径、权限、脱敏命令行、可获得的工作目录、退出时间和退出码。
- 官方日志中本次会话的资源检查、网页加载、登录、可开始状态，以及手动点击和本体创建时刻。
- 自动触发需要的窗口所属进程、类名、尺寸、控件等信息。

采集限制在本游戏安装范围、相关日志和已确认的进程链，不全盘扫描。使用规范化后的路径组件边界判断归属，处理跨盘、相似目录前缀、目录联接和 PID 复用，避免记录无关进程。轮询漏掉短命进程时注明缺口，必要时补充进程事件采集。读取不到的工作目录或其他字段标为未知，不能猜测补齐。

账号、令牌、Cookie、密码、票据和用户身份在写盘前脱敏；未知参数值默认隐藏，仅保留白名单中的非敏感值。不读取认证内存，不保存可复用的认证材料，不将原始敏感日志提交到仓库。固定样本使用相对路径和虚构身份。

先交付官方启动时间线和错误证据，区分“实机确认”“自动测试确认”“推断/未验证”，再进入桥接实现。

【第三阶段：扫描并核查官方启动参数】
依次检查真实快捷方式和进程命令行、官方说明、可读配置/日志/脚本/前端资源，必要时对安装范围内的官方二进制做只读参数字符串扫描。限制扫描范围与文件数量，不执行所有候选参数；即使 --help 也先评估是否会直接启动程序。

建立参数证据表：参数、来源、适用入口、含义假设、是否动态/敏感、实机结果、适用版本与渠道。
- 字符串中存在：只是候选，不能证明支持。
- 官方实际携带：证明曾使用，不能证明复制参数就足够。
- 官方文档说明：核对版本和适用范围。
- 实机对照成功：仅确认已覆盖的场景和功能。

分别核查参数是打开游戏页面、触发开始、向已有实例转发动作、维持 SDK 宿主，还是选择图形接口。发现 autoplay、skiplauncher 等名称时也必须验证完整功能和启动时序，不立即认定可用。不固化一次性票据，不把 Steam 尾随命令当作本体参数，不靠选项名称或着色器重编译推断实际渲染接口。

【第四阶段：基于证据选择桥接方案】
按需要选择，不强行采用同一种方式：
A. 本体及已验证的非敏感参数足够：直接启动本体。
B. 官方子入口能正确建立上下文：调用子入口，并继续跟踪真实本体，允许子入口提前退出。
C. 需要常驻官方 SDK/渠道宿主：保留宿主，按采集证据触发官方动作或包装入口。
D. 需要资源/网页/登录检查：启动官方入口，等待当前会话真正就绪，再触发同一实例的“开始游戏”。
E. 缺少可靠就绪或触发证据：保留可见的官方手动操作，说明缺口，不用猜测完成自动化。

特别注意两个不同问题：“是否等到官方检查完成”和“是否必须由官方启动器创建本体”。认证失败不能简单归因于没等够时间，也不能假定等几秒后自行创建本体就能通过。

典型教训：相同本体、命令行和工作目录，仍可能因启动时机过早而缺角色语音；直接复制官方参数，也可能因为缺少 SDK 上下文而认证失败。这些只是排查方向，不能当作本游戏已确认的事实。

需要等待时，将就绪证据绑定当前 PID/创建时间、日志会话及必要的线程/游戏标识，拒绝旧日志和其他游戏的状态。新会话、登录、更新、下载、维护或阻挡弹窗应使旧就绪失效。使用有超时的状态等待，不用固定休眠冒充检查完成；无法取得可靠标记时明确限制。

优先使用已确认的官方接口或可访问控件触发开始；坐标/窗口消息只作实测后的方案，配置化并注明版本和布局边界。触发前重新确认路径、窗口身份、就绪状态和阻挡情况；一次触发后等待本体，不循环盲点。登录、更新、错误或超时时恢复官方窗口并给出明确提示。

【第五阶段：工程要求】
- 默认 C++20、Win32、Windows x64、静态运行库，生成无需 .NET/Python 或额外 VC++ Runtime 的单文件 EXE。若仓库另有要求则遵守，并解释偏离默认方案的原因。
- 每款游戏独立目录，EXE 命名为 <英文项目名>LaunchBridge.exe，提供可重复执行的 Release 构建脚本。
- 从桥接 EXE 所在安装范围进行有限路径发现，可显式指定安装根。搜索有深度、数量和排除项限制，不写死版本目录或扫描整个磁盘。多候选冲突明确报错。
- 提供不含个人绝对路径的可选配置，覆盖本体/入口名称、参数、候选优先级、排除目录、搜索深度、超时、退出防抖和必要的 UI 兼容项。
- 使用对应游戏的多尺寸图标，保存 ICO 和可重复执行的提取脚本，不修改官方程序。
- 附着与跟踪同时核对进程名和完整路径，保留进程句柄读取退出码，处理进程接力和可配置退出防抖。
- 桥接器参数与 Steam %command% 尾随载荷隔离，不将未知参数透传给游戏/启动器。提权时让原桥接实例等待子实例，避免 Steam 提前结束跟踪。
- 明确重复启动与已有实例的处理策略，避免重复拉起游戏。不随意结束既有启动器；只隐藏/清理身份已核对且属于本次任务的窗口和进程。
- 游戏结束后先正常关闭自有启动器；任何强制结束前重新检查身份、是否有游戏重启及是否承载其他任务。不终止整个进程树、游戏或反作弊。
- 日志目录与 EXE 同级，命名为 <英文项目名>LaunchBridge-log；只用一个主要日志文件。启动时及长时间运行期间按条目清理七天前记录，不按日期或运行次数创建多个文件，不清空全部历史。
- 日志含 ISO 8601 时区时间、运行 ID/PID、版本/系统/架构、有效配置、候选/实际路径、脱敏命令和工作目录、状态转换、进程变化、退出码、运行时长、防抖及异常类型/消息/堆栈。日志写入失败的弹窗明确具体原因。

【第六阶段：测试、文档与交付】
自动检查至少覆盖：Release 编译、单文件与依赖、图标、有限路径发现、不同目录/渠道固定样本、同名异路径排除、Steam 尾随隔离、日志位置、精确七天保留和错误堆栈。
如果实现 Capture 或状态触发，还要覆盖脱敏、采集边界、旧会话拒绝、状态回退、登录/更新阻挡、超时、单次触发、进程接力与退出防抖。

实机以官方手动启动为基线，对照验证冷/热启动、登录、角色语音/音效、反作弊、官方图形设置、UAC、游戏退出和启动器清理。Steam 实际在线状态/时长与退出跟踪单独验证。无法完成的项目明确标为未验证，不用模拟进程测试替代。

提供：
1. 源码、构建脚本、Release EXE、示例配置、图标与提取脚本。
2. 按需制作的 Capture 源码/工具、采集步骤与脱敏固定样本。
3. 固定测试入口及实际运行结果。
4. 游戏 README 和实现原理文档，写明为什么需要桥接器、带日期/渠道的官方启动流程、方案与证据、配置/日志、更新失效边界、自动/实机范围和已知问题。
5. EXE 放置方式、双击及 Steam 使用方式、故障诊断方法。

按阶段持续推进，先收集证据再决定实现，不停留在计划。需要我配合时给出具体操作及完成标准；可以独立完成的工作继续做。每次反馈说明已确认内容、当前阻碍和下一步，不把推断写成事实。

最终说明采用哪种启动方式、关键证据、已执行检查、实机验证范围和待办。提交、推送、版本发布按我填写的范围和仓库规则执行；没有发布要求时交付本地产物，不擅自上传日志或发布 EXE。
```

## 在本仓库使用

本仓库的维护者还可配合 [开发 Skill](skills/game-launch-bridge/SKILL.md) 和 [已有桥接原理与采集模板](skills/game-launch-bridge/references/evidence-and-patterns.md) 使用。Prompt 保持独立可复制；具体游戏的最新结论以对应实现文档为准。

本仓库若执行推送或发布，须遵守 [AGENTS.md](../AGENTS.md) 中的双远程同步、推送记录、双端 Release、同一附件哈希和官网同步规则。其他项目应使用自己的发布规则，不需要照搬本仓库的账号和发布渠道。
